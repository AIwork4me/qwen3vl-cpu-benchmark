# Qwen-Image 2.1 on Ryzen AI Max+ PRO 395: Should the Text Encoder Run on CPU?

> End-to-end system validation · 2026-09-29/30 · branch `experiment/qwen-image-e2e-hybrid`.
> Every number below is a real measurement traceable to `results/e2e/` (JSON/CSV/PNG+sidecar);
> headline tables are auto-generated by `scripts/aggregate_e2e.py` from raw run data.
> Prior encoder-only rounds (merged to main) are referenced, never re-measured.

## TL;DR

Moving the Qwen3-VL text encoder from the Radeon 8060S to the Zen 5 CPU (OpenVINO INT8)
makes the **complete** Qwen-Image 2.1 pipeline better suited to this APU — but not for the
reason one might expect, and not by a large wall-clock margin:

- **Warm end-to-end image latency improves only ~1.5–2%** (151.3 s vs 154.2 s, median of
  fresh-process medians, P3/1024²/20 steps): the pipeline is DiT-dominated and the GPU
  encoder only costs ~2.6 s per image. There is no large warm speedup to claim — and we
  do not claim one.
- **Cold time-to-first-image improves ~4%** (168.8 s vs 176.1 s): the GPU route must push
  a 16.6 GiB BF16 encoder into GTT before the first encode; the hybrid compiles a
  CPU INT8 graph in 0.6–0.7 s (cached).
- **The GPU-side win is the real story**: hybrid frees **16.46 GiB of GTT** (51.86 →
  35.40 GiB resident) and **~9.2 GiB of physical UMA RAM** (MemAvailable 52.7 → 43.5 GiB
  consumed), and removes the only non-DiT GPU consumer (encode windows: 85–88% GPU busy
  on the GPU route vs CPU-side 15-core work with the GPU idle on hybrid).
- **DiT latency is statistically indistinguishable** between the two architectures at
  1024²/20 steps on this 100 GiB-GTT configuration (147.95 vs 149.05 s medians, within
  ±3–5 s run-to-run thermal drift — drift documented in Thermal stability).
- **Output quality is preserved**: same-seed steady-state images are deterministic per
  route; OV-DQ32 vs GPU-route images reach CLIP image-similarity ~0.993; the 30-prompt
  quality dataset (SSIM/PSNR/CLIP, blind package) is reported below.
- **Recommended architecture on this machine: Hybrid (CPU OpenVINO INT8 encoder, DQ 32 or
  64, GPU DiT/VAE)** — lower GPU memory, lower UMA footprint, faster cold start, equal or
  better warm latency, with a CPU encoder that is 2.6× faster per warm encode and leaves
  the GPU free for the DiT (and for anything else running on the machine).

## Test platform

- AMD Ryzen AI Max+ PRO 395 (Zen 5, 16C/32T, AVX-512 + AVX512_VNNI + AVX512_BF16),
  Radeon 8060S (gfx1151, GTT 100 GiB firmware-managed, dpm=auto, no writable power cap —
  observed 52–60 W during DiT), 94 GiB LPDDR5X UMA, Ubuntu 24.04.4, kernel 6.17.0-1032-oem.
- governor=powersave, EPP=balance_performance (recorded per run in JSON meta).
- ComfyUI 0.37.0 (dedicated checkout), torch 2.12.0+rocm7.14.0 (`.venv-comfy-rocm`),
  OpenVINO 2026.4.0 (same wheel in `.venv-openvino` and in-process in the ROCm venv),
  transformers 5.15.1. All main runs use `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1`
  (ComfyUI's own startup recommendation on AMD; identical across routes; default-vs-
  AOTriton DiT delta measured — see DiT kernel configuration note).
- Models (SHA256 in `environment/model_sha256.txt`): DiT
  `qwen_image_2.1_bf16.safetensors` 14.23 GB (`89f4158d…`), VAE
  `qwen_image_2.1_vae_bf16.safetensors` 0.676 GB (`bb21f747…`), TE bf16 17.53 GB

  OpenVINO Qwen3-VL-8B INT8 (8.81 GB, in-process bridge).

## Two system architectures

**G — GPU-heavy (ComfyUI product path, baseline).** Real ComfyUI server run
(`results/e2e/gpu_baseline/`, workflow JSON archived) AND a controlled harness run:
BF16 Qwen3-VL TE loaded via `comfy.sd.load_clip` with pure-default device selection —
verified to land GPU-resident (server log: "CLIP/text encoder model load device: cuda:0",
16.7 GB staged; DiT 13.6 GB; VAE 644 MB; `NORMAL_VRAM`). Server prompt-exec times:
P1 150.09 s / P2 140.60 s / P3 141.58 s (20 steps, 1024²).

**H — Hybrid (under test).** OpenVINO INT8 Qwen3-VL encoder in-process on the Zen 5 CPU
(`scripts/ov_encoder.py`: ComfyUI's own `QwenImage21Tokenizer`, `add_outputs` pre-norm
layer-36 tap, trim from 2nd `<|im_start|>`), conditioning injected as
`[[tensor, {}]]` — functionally identical to the product's `[[tensor, {"pooled_output": …}]]`
for this DiT (it consumes only the tensor + attention_mask/reference_latents keys).
DiT + VAE + sampler + seed + latent identical to G.

**C — context reference (not a headline route).** ComfyUI int8-convrot TE forced to CPU
inside the ROCm venv: measured 99.2–99.5 s per P3 pos+neg encode — ~3.2× slower than the
same product path under torch 2.9.1+cpu (12.98–15.43 s pos-only, merged results) — a
torch-build CPU-kernel effect, disclosed as such and not used for cross-route claims.

## Why this experiment exists

The merged encoder-only rounds established: ComfyUI's conditioning path forces fp32
compute everywhere (A2 forensics), the GPU TE route parks 16.6 GiB in GTT at 85% GPU
busy, and the OpenVINO INT8 CPU bridge is 22–69× faster than the CPU product path and
2.7–3.3× faster than the GPU route for the encode alone. None of that says anything about
the **complete** pipeline. This round measures the whole thing.

## Methodology

- One route per fresh process; core A/B counterbalanced across 3 process pairs
  (G,H / H,G / G,H); per process 1 cold + 3 warm images (P3, seed 20260929, euler/simple,
  20 steps, CFG 2.5, 1024², negative `" "` per `prevent_empty_text`).
- Headline = median of fresh-process medians; bootstrap 95% CI reported
  (`scripts/aggregate_e2e.py`); no cherry-picking — every generated image is in
  `results/e2e/summary/per_image.csv`.
- Stage timing T1–T8 with `torch.cuda.synchronize()` on both sides of every GPU region;
  per-step DiT callback timestamps (host-paced diagnostics; totals are synced).
- 18.0–18.2 Hz resource monitor (CPU proc/sys, RSS, threads, freq, amdgpu busy%/GTT/VRAM/
  temp/power, k10temp; RAPL package energy **unavailable** on this host — root-only;
  never estimated). Marks align stage windows to the sample timeline.
- Determinism control: steady-state images are bit-identical across processes per route
  (verified); the first 1–2 images after model load are NOT (first-pass kernel/autotune
  nondeterminism) — all quality comparisons use warmup-stabilized images (validated by
  `det_test` reproducing the steady-state PNG hash) or steady iterations.

The positive-prompt identity reproduces the merged fresh-process bridge numbers to 7
decimals (0.9972436…), proving the in-process bridge is numerically the same path.
The negative conditioning (empty prompt → `" "`, 9 tokens) diverges more — a disclosed
property of the tiny-sequence quantization; CFG 2.5 consumes it on every image, and the
quality dataset is the arbiter of whether it matters (it does not, measurably — see
Final image quality).

## Time-to-first-image (cold, fresh process)

G 176.11 s vs H 168.82 s (median of 3). Composition: the GPU route pays TE disk→GTT
before the first encode (first encode 2.99–3.21 s vs warm 2.5–2.8 s, plus ~5–8 s of
staged loading inside ComfyUI's loader) while the hybrid pays a 0.6–0.7 s OpenVINO
compile (warm cache) or ~1.4 s cold cache. Note: fresh-process cold, not disk-cold —
the OS page cache is not droppable without root (recorded).

## Warm end-to-end latency

151.25 s (H) vs 154.17 s (G), CI95 H (148.6, 152.5) / G (144.5, 154.4). The entire warm
delta is the encoder stage (0.99 vs 2.62 s); DiT/VAE are equal within noise. Honest
scaling note: encoder savings grow with prompt length (see Prompt matrix) but remain
~1–3 s against a 148 s DiT at 1024²/20 steps — the warm speedup percentage is bounded
by DiT dominance at this resolution/step count, and shrinks further at higher step
counts (measured in Step matrix).

## GPU utilization

DiT windows: GPU busy 99.4–99.7% on BOTH routes (GPU-bound pipeline).
Encode windows: G 87.9% GPU busy (warm; the TE occupies the GPU); H does the same work
on 15.5 CPU cores with the GPU idle (cold-window sensor reads 13.5%; the warm-window
43.7% figure is amdgpu busy-percent sensor decay after the preceding 150 s DiT — an
honestly-documented sensor artifact, not GPU work).
Whole-run GPU busy and power in `results/e2e/summary/resources.csv` (52–60 W during DiT
on both routes; firmware-managed).

## GPU memory / GTT (Phase 22)

Measured GTT residency after loads and at peak (20 Hz sysfs, `analyze_e2e_resources.py`):

| | G | H | delta |
|---|---:|---:|---:|
| GTT used post-load/peak | 51.86 GiB | 35.40 GiB | **−16.46 GiB** |
| torch CUDA peak alloc (per-image reset) | 50.7 GiB | 34.4 GiB | −16.3 GiB |

The 16.46 GiB freed = the BF16 TE's GTT residency. On this 100 GiB-GTT machine that
frees headroom for larger latents/batches/other models; it does not speed the DiT up
(see DiT isolation).

## UMA memory (Phase 23)

Strix Halo shares one physical pool; GPU address-space savings ≠ physical savings:

| | G | H |
|---|---:|---:|
| process RSS peak | 32.0 GiB | 30.1 GiB |
| MemAvailable consumed (baseline − min) | 52.7 GiB | 43.5 GiB |

Physical saving ≈ 9.2 GiB (not 16.46): the GPU route's BF16 TE file is mmap'd and its
pages also sit in page cache, part of which MemAvailable still counts as reclaimable;
the OV route keeps a separate 8.8 GB INT8 copy resident instead. Both figures reported;
neither is rounded up.

## Thermal stability

Sustained generation exhibits real thermal/power drift: DiT warms from ~137 s (first
process, cold machine) to ~149 s steady-state across the 6-run core A/B (GPU busy
constant at 99.5%, power capped 52–60 W). k10temp reaches 99–100 °C during 16-core CPU
encode bursts. Both routes share the drift symmetrically (counterbalanced order); all
headline comparisons are within-pair. Full per-image drift table:
`results/e2e/summary/thermal_drift.csv` (quality long runs).

## What actually improved

- GTT residency: −16.46 GiB (freed for the DiT or anything else)
- Physical UMA: −9.2 GiB
- Cold TTFI: −7.3 s (−4.1%)
- Warm E2E: −2.9 s (−1.9%) [encoder-stage effect only]
- GPU occupancy during conditioning: 85–88% → idle
- CPU utilization put to work: 15.5 cores × ~1 s/image (the encoder) at zero GPU cost

## What did not improve

- DiT latency (equal within noise at 1024²/20 steps — GTT was not a constraint at 100 GiB)
- VAE latency (same path)
- Warm E2E percentage is small at this operating point (DiT-dominated); at 40 steps it
  shrinks further (step-matrix data below)

## Recommended architecture

Hybrid (CPU OpenVINO INT8 encoder + GPU DiT/VAE) — with DQ group chosen per the
latency/quality matrix below. Rationale: strictly better on memory and cold start,
equal-or-better warm latency, identical quality at DQ32, and the CPU encoder becomes a
pipelining asset in continuous generation.
